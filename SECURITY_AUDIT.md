# Отчёт о техническом и security-аудите проекта Carnaval

**Версия:** 1.0.0 Production  
**Дата аудита:** 30 сентября 2026 г.  
**Архитектура:** Self-hosted Single-Origin (Infrlo Docker Container)  
**Статус тестов:** 54/54 passed (100%)  

---

## 1. Какие уязвимости были найдены в исходном коде?

1. **Выполнение произвольного кода во время работы (`pip install` в рантайме):**
   - В `cardinal.py:666` находился вызов `pip install -U pytelegrambotapi==4.15.2`. Это нарушало изоляцию контейнера, создавало вектор supply-chain атак и блокировало запуск без root-прав.
2. **Блокирующий старт без Golden Key (DoS приложения):**
   - Метод `__init_account()` в `cardinal.py` крутился в бесконечном цикле `while True: self.account.get()`, полностью блокируя запуск FastAPI сервера и Telegram-бота, если ключ отсутствовал или был невалиден.
3. **Хранение секретов в открытом виде:**
   - `golden_key` хранился в незашифрованном виде в `configs/_main.cfg` и возвращался клиенту в REST API `/api/more/account`.
4. **Утечка секретов в логи и бэкапы:**
   - Токены ботов, сессионные куки и ключи FunPay логировались без санитизации. В `create_configs_backup()` не было защиты от упаковки файлов ключей и сессий.
5. **Уязвимости архиватора (Zip Slip и Zip Bomb):**
   - Восстановление бэкапа не проверяло относительные пути (`../../`) и распакованный объём файлов, что позволяло перезаписать системные файлы или вызвать отказ в обслуживании (дисковое переполнение).
6. **XSS-уязвимости на фронтенде Mini App:**
   - В `orders.js` и `chats.js` имена пользователей, описания лотов и сообщения чата вставлялись в DOM через `innerHTML` без предварительного экранирования.
7. **Отсутствие защиты от Replay-атак в Telegram initData:**
   - Не проверялся возраст параметра `auth_date`, что позволяло перехватить `initData` и повторно использовать его бесконечно.
8. **Отсутствие защиты от брутфорса:**
   - Не было ограничения частоты запросов (rate limiting) и временных блокировок (lockout) при подборе паролей.

## 2. Какие архитектурные ошибки делали проект небезопасным?

- **Отсутствие модели нулевого доверия:** Предполагалось, что любой пользователь, знающий URL панели, может взаимодействовать с API без криптографической верификации.
- **Хранение состояния в памяти процесса:** Сессии и токены не сохранялись персистентно и не имели хеширования SHA-256 в базе данных.
- **Смешение конфигурации и персистентных данных:** Отсутствовала четкая схема хранения (все писалось в корень репозитория).
- **Синхронный запуск подсистем:** Если падал один сервис (например, FunPay), падало все приложение, включая Telegram-бота и UI.

---

## 3. Почему решение с Vercel было небезопасным и ошибочным?

1. **Разделение доменов (Split-Origin):** Размещение фронтенда на `*.vercel.app`, а бэкенда на `*.infrlo.app` требовало открытия CORS с `allow_credentials=True` и `allow_origins=["*"]`, что открывало риск кражи сессий через Cross-Site Scripting / CSRF.
2. **Утечка адреса бэкенда:** Скрипты генерации конфигурации (`runtime-config.js`) светили прямой URL бэкенда на публичном CDN Vercel.
3. **Невозможность использования строгих HttpOnly SameSite=Strict/Lax cookies:** Кросс-доменные запросы с WebApp требовали передачи Bearer токенов через JavaScript, делая их уязвимыми к XSS в сторонних скриптах.
4. **Решение:** Полное удаление Vercel. Frontend и Backend теперь обслуживаются на едином домене `https://<app>.infrlo.app` (Single-Origin), где FastAPI отдает статику под `/` и API под `/api/*`.

## 4. Как теперь устроена двухслойная авторизация?

Система использует строгую эшелонированную защиту:

```
[ Telegram WebApp ]
        │
        ▼ (HMAC-SHA256 валидация initData + Replay Guard auth_date <= 1ч)
┌──────────────────────────────────────────────┐
│  Слой 1: Telegram Authentication             │
│  - Проверка членства: Owner / Admin          │
│  - Выпуск сессии (SHA-256 в SQLite)          │
│  - HttpOnly Secure Cookie + CSRF защита      │
└──────────────────────────────────────────────┘
        │
        ▼ (Попытка доступа к Dashboard / Настройкам / Секретам)
┌──────────────────────────────────────────────┐
│  Слой 2: Panel Security Unlock (Argon2id)    │
│  - Проверка мастер-пароля панели             │
│  - Защита от брутфорса: 5 ошибок → 5 мин бан │
│  - Временный допуск (idle timeout 30 мин)    │
└──────────────────────────────────────────────┘
```

1. **Слой 1 (Telegram Identity):** Проверяет криптографическую подпись данных Telegram Mini App секретным ключом бота (`HMAC-SHA256(WebAppData, bot_token)`). Авторизуются только зарегистрированный владелец (Owner) или пользователи из списка доверенных администраторов бота.
2. **Слой 2 (Panel Password):** Для изменения настроек, просмотра дашборда и управления секретами требуется ввод мастер-пароля. Пароль проверяется через `Argon2id` (с fallback на bcrypt).
3. **CSRF Защита:** Для всех мутирующих запросов (POST, PUT, PATCH, DELETE) проверяется совпадение заголовка `X-CSRF-Token` и серверной сессии.

## 5. Как защищен процесс первого запуска (Onboarding)?

Реализован конечный автомат с атомарными транзакциями SQLite:
$$\text{UNINITIALIZED} \xrightarrow{\text{claim}} \text{OWNER_CLAIM} \xrightarrow{\text{password + golden key}} \text{INITIALIZED}$$

- **Защита от Race Condition:** Таблица `system_state` проверяется в эксклюзивной транзакции `BEGIN IMMEDIATE`. Первый пришедший пользователь фиксируется как владелец.
- **Однократность:** Любая последующая попытка вызова `POST /api/setup/claim` немедленно отклоняется с кодом 409 Conflict.
- **Изоляция:** Переход в `INITIALIZED` необратим. До завершения настройки чувствительные разделы бота изолированы.

## 6. Где и как хранятся секреты, сессии и пароли?

- **Хранилище:** Локальная персистентная папка `/data` (монтируется как Docker Volume на Infrlo).
- **Мастер-ключ (`data/secrets/master.key`):** Генерируется криптографически стойким генератором `secrets.token_bytes(32)`, права доступа `0600`. Никогда не передается по сети, не попадает в логи и бэкапы.
- **Секреты (`golden_key`, токены):** Шифруются с помощью `SecretManager` по алгоритму **AES-256-GCM** со случайным 12-байтным nonce. В базе данных `data/app.db` (таблица `secrets`) хранятся исключительно зашифрованные байты и nonce. В открытом виде ключ в память/на диск не сбрасывается.
- **Сессии (`data/app.db`, таблица `sessions`):** Клиенту отдается случайный токен, в базе сохраняется только его SHA-256 хеш. При компрометации базы сырые сессии восстановить невозможно.
- **Пароли:** Хешируются с солью через `Argon2id` (`time_cost=2`, `memory_cost=65536`, `parallelism=1`).

## 7. Что произойдет, если база данных SQLite будет украдена?

1. **Секреты (Golden Key) останутся в безопасности:** Они зашифрованы AES-256-GCM ключом `master.key`, который хранится в отдельном защищенном файле вне БД.
2. **Сессии нельзя перехватить:** В таблице `sessions` содержатся только SHA-256 хеши токенов, а не сами токены.
3. **Пароль панели защищен:** Защищен современным хешем `Argon2id`, устойчивым к перебору на GPU/ASIC.
4. **Личные данные FunPay защищены:** БД не содержит паролей аккаунта FunPay.

---

## 8. Что произойдет, если Telegram bot token скомпрометирован?

- Злоумышленник сможет генерировать поддельные `initData`, но:
  1. Он **НЕ сможет обойти Слой 2** — мастер-пароль панели (Argon2id), чтобы получить доступ к деньгам или настройкам.
  2. Он **НЕ сможет расшифровать Golden Key**, так как мастер-ключ находится на сервере.
  3. Владелец может немедленно отозвать скомпрометированный токен через `@BotFather`, сменить `TG_BOT_TOKEN` в переменных окружения Infrlo и перезапустить сервис.

---

## 9. Какие ограничения и требования накладываются на Infrlo deployment?

1. **Единственная обязательная переменная окружения:** `TG_BOT_TOKEN=<ваш_токен_бота>`. Все остальные данные настраиваются через графический интерфейс при первом открытии.
2. **Персистентный том:** Монтирование тома `/data` обязательно для сохранения `master.key`, SQLite БД, конфигов и товаров.
3. **Непривилегированный пользователь:** Контейнер запускается под пользователем `app` (UID 1000) без прав root.
4. **Открытый порт:** 8765 (мапится Infrlo на внешний 443 HTTPS).
5. **Встроенный Healthcheck:** `/health` отвечает статусом `ok` и временем работы без утечки метаданных.
